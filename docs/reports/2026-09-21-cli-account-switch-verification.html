1 · Flows as implemented

Both diagrams describe what the backend authority (backend/agent_team_backend/quota_failover.py) and the credential vault do today, as exercised by the contract tests in §5 — not the plan's wording.

1a · Switch transaction (renderer reports, backend decides)

  • Reports are trusted only from the backend's own per-account usage snapshot (usage-window) or a vendor-declared exhaustion text pattern (cli-text); as of 10:51 claude, muse, droid and mcode declare patterns (1 / 1 / 2 / 1); for the other eleven a cli-text report only notifies.
  • Automatic swaps are budgeted per credential pool: 3 per rolling 5 h, 10 min apart, persisted in navide.db; manual switches never count.
  • Terminal states (ready / notify-stopped) are published in recentIncidents / recentTransactions so a window can show the announcement and offer the manual switch-back.

1c · Runtime wiring (read-only check, 10:58)

  • Deadlines. quota_failover.tick is not polled by anything: _arm_timer (quota_failover.py:2502) schedules it with loop.call_later on the event loop the handler runs on, at the three points that need a deadline — prepare sent (:1972, 30 s), a busy ack parking the transaction (:2025, 30 min) and after a commit (:2313, 120 s). It therefore fires with usage polling disabled, for a vendor without fetch_usage, and with no renderer calling get_state. Proof with the real timers (deadlines shortened, no tick call): test_deadlines_fire_without_polling_or_a_renderer (row 31). The only path that arms nothing is a call outside a running loop, which the app never makes.
  • Handlers. quota_failover.get_state / set_policy / report / candidates / switch / confirm / ack / settle / cancel / reconcile are registered with @handler in ws_handlers.py and reached through app.handle_message — every contract test dispatches that way. The manual route calls on_manual_switch (ws_handlers.py:2342) and terminal.create records pane_auth_scope provenance (:6716).
  • Events. quota_failover.changed / commit go through app.broadcast (app.py:344, every session in _SESSIONS); quota_failover.prepare goes to the owning session's send_json. The contract tests record app.broadcast instead of opening sockets; the socket path itself is covered by existing transport tests that register real sessions (e.g. backend/tests/test_plans_changed.py). The renderer subscribes to the three event names in useQuotaFailover.ts:803-805 (frontend, not verified here).
  • Usage hand-off. Every reading the poller keeps reaches observe_usage through usage_service._notify_failover (:1193 claude per slot, :1240 other providers' active slot); readings dropped for a mid-read switch never do.
  • Startup. The authority is built at import with the app database (app.py:197) and reloads the unreconciled marker from it; the pending-login sweep runs as a startup task (app.py:1966). Observation, not a defect: incidents and open transactions are in-memory, so a backend restart while a restart-vendor switch is preparing forgets it (the window's late ack is answered NOT_FOUND); the persisted parts — policy, budget, unreconciled — survive.

3 · Isolated vs. global sign-in

isolated claude, codex, grok, kimi, pi, droid
The login pane gets a private home through an environment variable (Claude: CLAUDE_CONFIG_DIR; grok: a HOME shim). The CLI writes its fresh credential there; the live credential and every running pane are untouched. The switch handler and the usage poller harvest the home into the profile's slot; while the login pane still runs the switch is refused (LOGIN_IN_PROGRESS).
global antigravity, cursor, copilot, kilo, opencode, qwen, muse, aider
No environment lever exists (one machine-wide store, or only a generic XDG variable). The sign-in replaces the live credential. Since 2026-09-21 the vault snapshots the active account's live credential before the pane spawns (.pre-login-live.json in the profile's slot directory); the harvest then parks what the CLI wrote into the new profile's slot and restores the snapshot, so the account that was active stays active and its slot is never overwritten. Removing the abandoned profile mid-login discards the pending login the same way. The handler-side guards landed at 10:43: a global login pane is refused while other panes of the CLI run (LOGIN_BLOCKED_BY_LIVE_PANES, the snapshot is discarded), "login pending" is judged by the snapshot (vault.login_pending) rather than a login-home directory, and a regular pane of the CLI is refused while a global sign-in is pending (LOGIN_IN_PROGRESS).

4 · Failures reproduced, fixed, and still open

Every item was first reproduced by a contract test against the real WS dispatch (app.handle_message), a throwaway navide.db, and the real stores; secrets are fake strings, the Keychain is the test suite's in-memory stand-in. Fixes were made by the owning panes; the assertions were never loosened to match behaviour.

fixed Turning auto off while a hot commit waited for the switch lock left the incident in switching
set_policy(off) cancelled the transaction but not the incident; _commit stood down silently. Fix: a single _withdraw() for policy change / cancel / manual switch and _settle_stopped() after a refused lock re-check. Test: test_auto_turned_off_while_the_switch_lock_is_held_does_not_swap (+ positive twin that the lock wait itself does not refuse).
fixed Credentials moved A → B but persisting the default failed: the next switch captured live B into A's slot
Both the legacy cli_profiles.set_default and quota_failover.switch took the store's "current" (A) as the outgoing account and would have mirrored B's live credential over A's only copy. Fix: a persisted unreconciled marker (rebuilt from navide.db on restart) makes both routes refuse with UNRECONCILED_STATE; the public quota_failover.reconcile request writes the store's default to the account that is live without moving credentials, then lifts the block. A caller naming a different slot than the record knows is refused (BAD_REQUEST, zero mutation). Test: test_partial_commit_never_lets_a_later_switch_capture_live_b_into_slot_a, including a backend restart in the middle and the switch back A ← B afterwards.
fixed (vault side) "Add account → sign in" on a CLI without login isolation cost the active account
antigravity / cursor / copilot / kilo: the login pane wrote over the live credential; the poller only fills an empty active slot, so B landed nowhere; switching to B then captured B into A's slot and restored B's empty slot — signed out, A lost. Fix (vault): pre-login snapshot, park-and-restore harvest, login_pending / discard_pending_login; cli_profiles.delete mid-login restores A. Tests: test_add_account_login_must_not_cost_the_active_account, test_cancelling_a_live_login_keeps_the_active_account (4 vendors each) — green against the vault at 10:40.
fixed (handler side, 10:43) Handler guards keyed on a login-home directory
For the same four vendors: (1) cli_profiles.set_default let a switch proceed while the profile's sign-in pane was still running, because LOGIN_IN_PROGRESS was only checked when a login home directory existed; (2) terminal.create spawned a global login pane while other panes of that CLI were running, although the sign-in replaces the credential those panes use. Fix: LOGIN_IN_PROGRESS now also fires for any running live-store login pane of the agent and the pre-switch harvest keys on vault.login_pending; a global login spawn with live regular panes is refused with LOGIN_BLOCKED_BY_LIVE_PANES{count} and the just-taken snapshot is discarded; a "live drift" check before a manual switch adopts a live login into an empty target slot or refuses with LIVE_DRIFT (owner's tests; not covered by the verification pane). Tests: test_switching_while_the_sign_in_pane_still_runs_is_refused, test_live_login_is_refused_while_other_panes_of_the_agent_run — 28/28 green (row 29).
fixed (frontend) Restart path rebuilt the xterm and lost the pane's scrollback
Reported by the frontend integration (10:43): reusing rebuildPaneViaResume created a new xterm, so the CLI's resume reprint would have stood in for the history; the coordinator rejected that as a silent downgrade of the plan's Phase D requirement. Fixed with an in-memory scrollback handoff: the restart still rebuilds the pane with a new xterm instance, but the old instance's whole buffer is serialised first and replayed into the new one, and the pane keeps its position and lineage — it is not the same terminal instance (§9 for the mechanism and its visible limit: the divider line is English only). Covered by the owner's useTerminal.scrollbackHandoff and App.quotaFailover tests (in R-4); to be seen on a real pane in the manual acceptance (§8) — no UI automation here.
fixed test_osplat guard: platform branch in quota_failover.py / cli_vendors/base.py
Found by the pre-integration full pytest run; moved behind the osplat seam by the owners (allow-listing was ruled out). Guard now 69 passed.
fixed Live-drift guard treated a token refresh as a different account
The first LIVE_DRIFT guard compared the whole credential payload, so an ordinary OAuth refresh of the active account (Claude Code refreshes hourly) blocked every later manual switch. Fix: identity comparison — a stable account id first (codex tokens.account_id or the id_token's chatgpt_account_id claim; claude oauthAccount.accountUuid / organizationUuid), then the email, else unverifiable: LIVE_DRIFT{verified:false}, which a manual switch may override with assume_live_is_current:true (automatic never does). Tests (real vault, both entry points): same-account refresh switches and keeps the refreshed tokens in A's slot; a different email, or the same email under another account id / organisation, is refused with zero mutation — claude and codex, manual and failover routes (rows 33–39, then 40 rows green in the re-verification).
fixed The manual "assume live is current" confirmation was not bound to the state it confirmed
For a credential that carries no identity, LIVE_DRIFT{verified:false} asks the user to confirm that the live credential is still the active account's. The first re-send (assume_live_is_current:true) on the legacy route carried nothing else, so a confirmation given for one state could be applied after another window had switched accounts, or after the CLI had replaced the live credential while the dialog was open. Fix (both routes): the refusal returns currentSlotId, epoch and an HMAC liveFingerprint; a confirmation must echo all three and is checked under the switch lock before any capture — BAD_REQUEST when one is missing, STALE_STATE / STALE_EPOCH / LIVE_DRIFT when one no longer matches; the renderer re-sends the values verbatim or not at all. Tests (opaque codex credential, real vault): honest re-send succeeds and keeps the confirmed credential in A's slot; bare assume, missing fingerprint, wrong fingerprint, live replaced during the dialog (same slot, same epoch), another window's switch, and an A → C → A round trip that lands on the same slot with only the epoch moved — each refused with zero mutation.
fixed New live-login guard crashed terminal.create for an opaque foreign owner
Found by the final full pytest run: _running_live_login_terminals read owner.terminals on every _PTY_OWNERS entry; an owner object without that attribute (the existing test_terminal_replace_dedup contract for another window's PTY) raised inside every pane spawn. Targeted rerun confirmed it was not a flake; fixed with a defensive lookup and green in the re-verification.
closed as a documented limit Copilot storeTokenPlaintext mode
With storeTokenPlaintext: true in Copilot's settings the token location cannot be established from the bundle. The vault refuses any read, switch or sign-in mutation in that mode (CredentialVaultError, config and slots untouched); the default pointer mode switches normally. This is a mode limit, not "Copilot unsupported" (vendor tests, 1109 passed in the owner's subset).

Problem and root cause

Codex was declared as requiring a session marker. The renderer therefore sent <!-- agent-team-session: at-pane:… --> as a real prompt when opening an otherwise empty pane. This could start model work, consume quota and produce an irrelevant response before the user had requested a task.

A second issue undermined passive attribution. CodexHomeManager prepared a pane home, but generic skills reconciliation subsequently mirrored unrelated entries from the global Codex home. This could make sessions and SQLite runtime files shared across panes. A pane-shaped path then did not establish which pane owned a conversation.

Codex 0.155.1 allocates a thread ID during initialization, while its rollout can be deferred and SessionStart is queued until the first turn. An internally allocated ID is therefore not a guarantee that a PTY host can observe it immediately.

Expected behavior: an idle pane may have no known session ID. The integration does not invent an ID, guess from a shared workspace, or create a model turn to fill that gap.

Review finding caught and fixed

Independent review found a P2 compatibility problem in the first isolation approach: simply stopping all sibling mirroring would also hide named profiles and relative configuration resources, such as agents/researcher.toml and custom instruction files.

The final implementation keeps sharing under CodexHomeManager and excludes known runtime storage there. It preserves resource visibility without making the skills subsystem responsible for the whole home. Regression coverage includes nested resources, late-added profile files during resume, local overrides, and new, already isolated and already shared runtime paths.

No remaining P1 or P2 findings were identified in the final task review. That review covers this bounded change; it is not an audit of unrelated worktree changes or future Codex storage formats.

Manual acceptance still required

The repository prohibits UI automation. The following actual-app checks remain assigned to the user:

  1. Idle startup: open an empty Codex pane with no role or kickoff. Wait for startup to settle. Confirm no HTML marker is submitted, no model work starts for discovery, and no marker-specific waiting overlay blocks input.
  2. First real task: enter a normal task in a newly prepared pane. Confirm the session ID becomes available once the CLI writes its rollout, and that the pane/history association survives an app restart.
  3. Concurrent panes: open two Codex panes in the same workspace, submit different tasks in reverse order, and confirm each retains its own session identity and resume target.
  4. Rebuild and restore: exercise fresh rebuild and fresh restore. Confirm no legacy marker reappears. Resume a confirmed historical conversation, including one in an existing shared Codex home, and confirm it returns to the original conversation/home without a new bootstrap turn.
  5. Configured prompts and resources: launch with an intentional role/task and, where used, a named Codex profile or custom agent configuration. Confirm those inputs and resources remain available without an appended marker.
  6. Legacy shared home: where applicable, review the Navide hook through Codex's own review flow. If the hook is disabled or untrusted and no trustworthy attribution source exists, an unknown ID is the expected safe result.

Preservation and limitations

  • Existing shared homes and their data were not migrated, detached or repaired. Existing local files and symlinks are preserved.
  • No real global configuration was changed during verification. YOLO mode does not approve hooks, and no global hook-trust bypass was added.
  • A shared path or matching workspace alone cannot bind a new Codex conversation. An enabled, trusted and validated callback may still be necessary for older shared homes.
  • The runtime-storage contract is pinned to Codex 0.155.1. Explicit user storage-location overrides and future new storage names are outside the automatic isolation guarantee.
  • Historical marker reading, explicit resume identity, other vendors and intentional prompts remain supported.
  • No commit, merge, deployment or manual UI acceptance is claimed.
